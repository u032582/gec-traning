# 模範: タスク1「延滞一覧」のPR と レビュー往復の見本

> これは**答えのコードではありません**。この週の主役は「PRを出してレビューの往復をこなす」ことなので、
> 見本も「**良いPR本文**」と「**指摘への向き合い方**」の例を示します。実装は自分で書いてください
> （実装のヒントは [tasks/01-overdue-list.md](../tasks/01-overdue-list.md) の「着地点のヒント」に）。

---

## 1. 良いPR本文の例

```
## やったこと
- 延滞一覧API GET /api/lendings/overdue を追加
- LendingMapper.findOverdue（returned_at IS NULL AND due_date < :today）
- LendingService.findOverdue（今日の日付を受け取り Mapper を呼ぶ）
- LendingController に GET /api/lendings/overdue を追加（LocalDate.now() を渡す）
- LendingService の単体テストを3本追加

## なぜこの実装か
- 日付を Controller で決めて Service に渡す形は、既存の lend/returnBook と同じ流儀に合わせた
  （テストで日付を固定できるため）
- 延滞判定は SQL 側の WHERE で行い、Java で全件取ってから絞る形にはしなかった（件数が増えても軽い）

## 動作確認
- schema.sql のサンプルで GET /api/lendings/overdue を実行
- 人月の神話（due_date=2026-07-04・未返却）が含まれ、返却済みのノルウェイの森は含まれないことを確認
- ./gradlew test 全緑（既存テストも緑のまま）

## 影響範囲
- 新規追加のみ。既存の貸出取得・貸出/返却には手を入れていない
```

> ポイント: 「なぜこの実装か」に**既存の流儀に合わせた理由**が書いてある。「動作確認」に**具体的にどのデータで確かめたか**が書いてある。レビュアーが再現・納得しやすい。

## 2. レビュー指摘への向き合い方の例

### 指摘例A（よくある）
> レビュアー:「`findOverdue` のテスト、延滞を含むケースはありますが、"期限がまだ来ていない貸出は含まれない" ケースが無いようです。」

**良い返し方**:
> ご指摘ありがとうございます。確かに「期限前は除外される」保証がテストに無く、`due_date < today` の `<` を誤って `<=` などにしても気づけない状態でした。期限が未来の貸出を混ぜたケースを1本追加し、結果に含まれないことを確認しました（`./gradlew test` 緑）。

- ✅ 指摘の**意味を自分の言葉で言い直している**（理解している証拠）
- ✅ **なぜそれが問題か**（境界の誤りに気づけない）を補っている
- ✅ どう直し、どう確認したかを返信している

**悪い返し方**（これは避ける）:
> 直しました。（← 何をなぜ直したか説明が無い。AIで再生成しただけかもしれない、と疑われる）

### 指摘例B（設計の相談になるもの）
> レビュアー:「並び順は指定が無いと不定です。延滞一覧なら、何か順序を決めた方が親切では？」

**良い返し方**:
> おっしゃる通りです。督促に使う想定なので「延滞が長い順（due_date 昇順）」が自然と考え、`ORDER BY due_date` を足しました。仕様には明記が無かったので、この意図で良いか確認させてください。

- ✅ 指摘を受けて**自分で判断し、その理由を述べ**、確認を取っている（盲従でも無視でもない）

## 3. 自己チェック（PRを出す前に）

- [ ] 受け入れ基準（tasks/01 の§2）を全部満たしたか
- [ ] `curl` で自分で動作確認したか（結果を PR に書けるか）
- [ ] `./gradlew test` が全緑か（既存も壊していないか）
- [ ] PR本文に「やったこと・なぜ・動作確認・影響範囲」を書いたか
- [ ] コミットは意味のある単位か

> これを**自分で満たしてから**レビューを依頼するのが現場の礼儀です。出す前の自己チェックまでが実装の一部。

---

## 4. この見本で見てほしいこと

- PR本文は「レビュアーが再現・納得できる」ように書く。特に**なぜその実装か**と**影響範囲**。
- 指摘には「**意味を言い直す→なぜ問題か→どう直したか**」で返す。黙って直さない、AIで作り直すだけにしない。
- 納得できない/仕様が曖昧な指摘は、**根拠を示して相談**する。盲従も無視もしない。
- 出す前に**自分で受け入れ基準を満たす**。これが週5〜8で鍛えた検証の集大成。
