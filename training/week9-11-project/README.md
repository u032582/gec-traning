# 週9〜11: 実戦プロジェクト — 既存システムへの参画を一人で回す

ここが研修の**本番**です。週5〜8で身につけた「AIと協働する作法」「読む・直す・テストで守る」を、**すべて統合**します。3週間かけて、[題材リポ（図書貸出管理API）](../project-repo/)に**複数の機能を追加**し、そのたびに**PRを出し、レビューの往復をこなして、マージ可能な状態まで持っていく**——現場で配属された新人が実際に任される動きそのものを、通しで練習します。
全体の進め方・AI利用ルール・質問テンプレート・日報フォーマットは、先に [研修トップのREADME](../README.md) を読んでください。

> この3週間の主役は **「PRとレビューの往復」** です。「一発で完成」を目指すのではありません。**講師がレビュアー役として、実際に指摘を返します**。その指摘にどう向き合い、どう直し、どう再説明するか——技術力と同じくらい、この**往復の質**が問われます。

---

## 1. この3週間の狙い（到達目標）

> **既存システムへの参画を一人で回せる——仕様を読み、AIを使って実装・テストし、PRを出し、レビューの往復をこなして取り込まれるところまで。**

「ゼロから全部作る」ことは求めません。**既存の流れに乗って、壊さず、確実に前に進める**こと。これが現場の新人に求められる姿です。

この3週間で統合するもの:

- **仕様を読んで実装する**（週3〜4）: タスクの仕様書を読み、既存の3層に馴染む形で機能を足す
- **AIと協働する**（週5）: 実装・テストにAIを使い、生成物を検証・説明する
- **既存コードを読む**（週6）: どこに足せば自然か、影響範囲はどこかを、コードから判断する
- **壊さず直す**（週7）: 既存テストを緑に保ち、リグレッションを出さない
- **テストで品質を守る**（週8）: 追加機能に意味のあるテストを付ける
- **PRとレビューの往復**（今週の新要素）: コミットを意味ある単位で切り、PR本文で説明し、指摘に往復で応える

---

## 2. AI利用区分（この期間のルール）

✅ **週9〜11は、AIを全面的に使ってよいです（現場想定）。** ただし**説明責任は常に伴います**。

- ✅ 実装・テスト・PR本文の下書き・レビュー指摘への対応案、すべてAIに相談してよい
- ✅ ただし**出したコードは自分の言葉で説明でき**、レビュー指摘に「なぜそう直すか」を自分で答えられること
- 🚫 「AIがこう書いたので」はレビューの返答として不可。**判断の主語は常にあなた**

> 現場では、AIを使うこと自体は当たり前になります。差がつくのは「**AIの出力に責任を持てるか**」。レビュアーの指摘に対して、AIに丸投げで再生成するのではなく、「その指摘はこういう意味だから、こう直した」と自分で説明できる人が信頼されます。この3週間は、その練習です。

## 3. この期間の進め方（1タスクのサイクル）

各タスクは、次のサイクルで進めます。**このサイクル自体が今週の学び**です。

1. **タスク仕様を読む**: `tasks/NN-xxx.md` を開き、何を作るか・受け入れ基準を把握する。
2. **着地点を決める**（週6の読解）: 既存リポのどこに足すのが自然か、影響範囲はどこかを見極める。
3. **ブランチを切る**: `git switch -c feature/xxx`（週7のGitフロー）。
4. **実装する**（AI協働）: 既存の3層・命名に馴染む形で実装。テストも足す（週8）。
5. **自分で受け入れ基準を確認**: 各タスクの「動作確認（curl）」と「全テスト緑」を**自分で**通す。
6. **PRを出す**: PR本文に「やったこと・なぜこの実装か・動作確認・影響範囲」を書く。
7. **レビューの往復**（今週の主役）: 講師（レビュアー役）の指摘に対応し、修正して再提出。**マージ可能になるまで往復**する。
8. マージされたら次のタスクへ。

> ⚠️ **ステップ5を飛ばさないこと。** 「自分で受け入れ基準を満たしてからレビューを依頼する」のが現場の礼儀です。動作確認もせずにPRを出すと、レビュアーの時間を奪います。**出す前に自分で確かめる**——週5〜8で鍛えた検証の癖を、ここで使います。

## 5. この期間の完了判定（自己採点 ＋ レビュー）

- [ ] 少なくとも2タスクを、PRを出し**レビューの往復を経て**マージ可能な状態にした
- [ ] 各PRで、受け入れ基準（動作確認・全テスト緑）を**自分で確認してから**依頼した
- [ ] レビュー指摘に対し、「なぜそう直すか」を自分の言葉で説明して対応した
- [ ] コミットが意味のある単位で切られ、PR本文で変更が説明されている
- [ ] レビュー往復の記録（指摘→対応）が残っている

> **完了の本質は「マージされたPRの数」ではなく「レビューの往復をきちんと経験したか」**です。1タスクでも、指摘を受けて直して再説明する往復を最後まで回せたら、それは大きな前進です。

## 6. レビューの往復のコツ（今週の主役なので厚めに）

現場のレビューは「ダメ出し」ではなく「一緒に良くする対話」です。指摘への向き合い方:

- **指摘は人格否定ではない**: コードへの指摘であって、あなたへの攻撃ではありません。落ち着いて受け取る。
- **意図を確認してよい**: 指摘の意味が分からなければ「これはこういう理解で合っていますか？」と聞く。憶測で直さない。
- **直したら、何をどう直したかを返信する**: 「ご指摘の通り、〇〇を△△に変えました。理由は〜」と、**対応を言葉にして**返す。黙って直すだけにしない。
- **納得できない指摘は、議論してよい**: 「こう考えて今の実装にしましたが、いかがでしょう」と根拠を示して相談する。盲従も無視もしない。
- **小さく直して再依頼**: 一度に全部直そうとせず、指摘に対応したら再レビューを依頼する。

> このコミュニケーションは、[研修トップのREADME](../README.md) の「報連相」の実践そのものです。技術力と同等以上に、現場で効いてきます。

## 7. Git / PR（週7のおさらい）

同一リポでブランチを切ってPR、が基本（**フォークは使いません**）。
```bash
git switch -c feature/overdue-list      # ①ブランチを切る
# …実装。こまめにコミット（feat: 始まり）…
git fetch origin                        # ②origin/master を最新化
git push -u origin feature/overdue-list # ③push
# ④PRを作る → ⑤レビュー往復 → ⑥master へマージ
```
詳しくは [週7のGitフロー](../week7-safe-modification/README.md#7-git--pr-のおさらい週7以降ずっと共通) と [週4のGit手順](../week4-test-and-final/README.md#6-git--prプルリク提出の手順--初心者向け)。
