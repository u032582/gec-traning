# タスク1: 延滞一覧API（GET /api/lendings/overdue）

**難易度**: ★☆☆（新しい読み取りを1本足すだけ。既存を壊しにくい）
**AI利用区分**: ✅ 全面解禁。ただし説明責任を伴う。

---

## 1. 背景（なぜこの機能が要るか）

図書館の運用では「返却期限を過ぎているのに、まだ返っていない貸出」を一覧したい場面があります（督促のため）。いまのAPIには、この一覧を取る窓口がありません。そこで**延滞一覧API**を1本追加します。

> 週8で `OverdueChecker`（延滞判定）を扱いましたね。その「延滞」を、DBから一覧で取る機能です。

---

## 2. 仕様（受け入れ基準）

### エンドポイント
```
GET /api/lendings/overdue
```

### 返すもの
「**返却期限（due_date）が今日より前**」かつ「**まだ返却していない（returned_at が NULL）**」貸出の一覧。

- 各要素は既存の `LendingResponse` の形（貸出の情報）でよい。
- 並び順は「期限が古い順（延滞が長いものが先）」が望ましい。
- 該当が無ければ空配列 `[]` を返す（エラーにしない）。

### 受け入れ基準（これを満たせばOK）
- [ ] `GET /api/lendings/overdue` が 200 で、延滞している貸出だけを返す
- [ ] 返却済み（returned_at あり）の貸出は含まれない
- [ ] 期限がまだ来ていない貸出は含まれない
- [ ] 単体テスト（Service層）を足し、`./gradlew test` が**全緑**
- [ ] 既存のテストを壊していない

---

## 3. 着地点のヒント（週6の読解を使う）

既存の貸出取得（`GET /api/members/{id}/lendings`）の流れを思い出してください。同じ3層に、1本足すだけです。

- **Mapper**: `LendingMapper` に「延滞の貸出を取る」メソッドを1つ足す（XMLに `WHERE returned_at IS NULL AND due_date < #{today}` のSQL）。
- **Service**: `LendingService` に、今日の日付を渡して上記を呼ぶメソッドを足す。
- **Controller**: `LendingController` に `GET /api/lendings/overdue` を足す（`LocalDate.now()` を Service に渡す形は、既存の `lend`/`returnBook` と同じ流儀にする）。

> 「今日の日付」を Controller で決めて Service に渡すのは、既存コードと同じ作法です（テストで日付を固定できる）。**既存の流儀に合わせる**のがこのタスクの隠れた採点ポイント。

---

## 4. 動作確認（自分でやってから、PRを出す）

`db/schema.sql` のサンプルデータには、期限切れ・未返却の貸出が含まれています（`人月の神話` の貸出など、due_date が過去のもの）。

```bash
# アプリ起動後
curl http://localhost:8080/api/lendings/overdue
# → returned_at が null で due_date が今日より前の貸出だけが返ること
```

> サンプルデータの日付は固定です。今日の日付によっては「まだ延滞していない」ものもあるので、**どの貸出が延滞に該当するか**を schema.sql を見て自分で予想し、curlの結果と突き合わせてください。

## 5. レビュー観点（レビュアーが見る＝出す前に自分でも確認）

- **既存の流儀に馴染んでいるか**: 日付の渡し方・命名・3層の分け方が、既存の lending コードと揃っているか。
- **SQLの条件が正しいか**: `returned_at IS NULL` と `due_date < today` の**両方**があるか（片方だけだと延滞でないものが混じる）。
- **テストが意味を持つか**（週8）: 「延滞は含む・返却済みは含まない・期限前は含まない」を確かめているか。呼ぶだけのテストになっていないか。
- **影響範囲**: 既存の貸出取得に影響していないか（新規追加なので基本無いはずだが、共通部分を触っていないか）。
