> 全体の講師向け方針は [for-instructors.md](../../for-instructors.md) を参照。ここは週9〜11のタスク別・レビュー実務に特化します。

## 0. この期間の主役は「往復」（一発マージさせない）

curriculum.md と [for-instructors.md](../../for-instructors.md) のとおり、この3週間は **PRとレビューの往復** が主役です。

- **一発でマージしない**。どんなに出来が良くても、**最低1往復**は指摘を返して、新人に「指摘に向き合い・直し・再説明する」経験をさせてください。
- 見るのは**指摘の質より、新人の向き合い方**: 指摘をどう受け取り、どう直し、「なぜそう直したか」を再説明できるか。
- **AIへの丸投げ再生成を見抜く**: 指摘に対し、理解せずAIで作り直しただけの再提出は、説明を求めて止める。「その変更は何をしているか」を言わせる。
- 進度に幅が出てよい。**課題数より往復の質**。1タスクを往復しきる方が、4タスク一発マージより価値がある。

## 1. 共通のレビュー観点（全タスク）

どのタスクでも、次を最低限見てください（新人にも各タスク仕様の「レビュー観点」として開示済み）。

- **既存の作法に馴染んでいるか**: 3層の分け方・命名・DTO分離・日付の渡し方が、既存コードと揃っているか。浮いた実装は指摘する。
- **PR本文の説明力**: 「やったこと・なぜこの実装か・動作確認・影響範囲」が書けているか。薄ければ「なぜこの実装にしたか」を問う。
- **テストの意味**（週8の応用）: 追加テストが「呼ぶだけ」「トートロジー」になっていないか。意味のあるアサーションか。
- **全テスト緑・リグレッションなし**（週7の応用）: `./gradlew test` が全緑か。既存を壊していないか。
- **コミットの粒度**: 意味のある単位で切られているか。

> **わざと1つ、指摘の"種"を残す**のも手です（完璧なPRでも「テスト名がもう少し意図を表すと良い」等）。往復を必ず発生させるため。

## 2. タスク別・指摘の狙いどころ

### タスク1: 延滞一覧（★☆☆）
- **狙い**: SQLの条件が `returned_at IS NULL` と `due_date < today` の**両方**あるか。片方だけだと延滞でないものが混じる。ここが抜けていたら指摘。
- 日付を Controller で決めて Service に渡す既存流儀に合わせているか（テスト容易性）。合っていなければ問う。
- よくある不足: 「返却済みを除外」のテストが無い。あれば良、無ければ「返却済みが混じらない保証は？」と問う。

### タスク2: カテゴリ別集計（★★☆）
- **狙い**: 集計を **SQLの GROUP BY** でやっているか。Javaで全件取ってループ集計していたら「データが増えたら？」と影響を問う。
- `titleCount`（行数）と `totalCount`（合計）の取り違えが起きやすい。数字を1つ手計算で検算して確認。
- パス衝突: `/api/books/{id}` と `/api/books/stats/by-category` の競合を意識できているか。

### タスク3: 貸出上限（★★☆）※既存に手を入れる
- **狙い（最重要）**: 上限チェックが **在庫を減らす前** にあるか。後にあると「上限で断るのに在庫だけ減る」不整合。ここは**必ず**確認し、位置が違えば指摘。
- 「未返却の」冊数を数えているか（`returned_at IS NULL`）。返却済みまで数える実装は指摘。
- マジックナンバー `5` が直書きでないか。
- **リグレッション**: 既存の貸出テストが全緑か。上限未達の貸出を壊していないか。境界（4冊OK/5冊NG）のテストがあるか。

### タスク4: 予約（★★★）※設計から
- **狙い**: 正解が1つでないぶん、**設計判断の理由**を必ず問う。「重複予約を許すか」「在庫ありのとき予約を許すか」「statusを持たせるか」——新人が**決めて理由を言えるか**を見る（どちらの判断でも、理由が筋なら可）。
- schema追加が既存の書き方（FK・DROP順・コメント）に揃っているか。既存テーブルを壊していないか。
- 新パッケージが book/lending の構成をなぞれているか。浮いていれば指摘。
- 異常系（存在しない本/利用者）を既存の `common/` 例外で扱えているか。

## 3. 往復の閉じ方（マージ可能の判定）

次がそろったら「マージ可能」としてよい（研修上のゴール）。

- 受け入れ基準を満たし、`./gradlew test` 全緑、リグレッションなし。
- レビュー指摘に対応し、**新人が「何をどう直したか」を説明**できている。
- PR本文で変更が説明され、コミットが読める粒度。

> 実際にマージするかは運用次第（研修リポの master 保護に従う）。**大事なのは往復を経てマージ可能な状態に到達した記録が残ること**。新人の完了判定（README §5）と対応しています。

## 4. 新人が詰まったときの導線

- 実装で詰まる → 週6の読解ノート（着地点の地図）と各タスクの「着地点のヒント」に戻す。
- 壊してしまった → 週7の影響範囲の考え方＋`./gradlew test` で赤を読む。
- テストが書けない → 週8のテスト品質＋題材リポの既存テストをお手本に。
- レビューへの向き合いで固まる → README §6「レビューの往復のコツ」に戻す。技術より姿勢の問題なら、そこを言葉で支える。
