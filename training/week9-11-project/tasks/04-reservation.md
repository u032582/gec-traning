# タスク4: 予約機能（貸出中の本を予約する）

**難易度**: ★★★（**新エンティティを設計から追加**。このプロジェクトで一番大きい）
**AI利用区分**: ✅ 全面解禁。ただし説明責任を伴う。設計判断は自分が持つ。

---

## 1. 背景（なぜこの機能が要るか）

在庫0（全部貸出中）の本を借りたい利用者が、「返ってきたら借りたい」と**予約**できるようにしたい、という要望です。これは新しい概念（予約）の追加なので、**テーブルから設計**します。既存の books/members/lendings に、`reservations`（予約）を1つ加えるイメージです。

> これまでのタスクは「既存の形に沿って足す」でした。このタスクは**設計から自分で決める**部分があります。正解が1つではないので、**設計判断とその理由**が問われます。週3〜8で見てきた既存コードの作法を、自分で新エンティティに適用してください。

---

## 2. 仕様（受け入れ基準）

最低限、次を満たす「予約」を実装します。**設計の細部は自分で決めてよい**（決めた理由をPRで説明する）。

### 最低限の機能
- **予約する**: `POST /api/reservations`（誰が・どの本を予約するか）。在庫があるなら「借りればいいので予約不要」として断る、という判断を入れてもよい（入れるかは設計判断）。
- **予約一覧**: ある本の予約、またはある利用者の予約を取得できる（どちらか一方でも可）。

### テーブル（設計の出発点。列は自分で調整してよい）
```
reservations
  id          … 主キー
  book_id     … 予約した本（FK → books）
  member_id   … 予約した人（FK → members）
  reserved_at … 予約日
  status      … 予約の状態（例: waiting / canceled など。持たせるかは設計判断）
```

### 受け入れ基準
- [ ] `reservations` テーブルを `db/schema.sql` に追加した（既存の書き方＝DROP順・FK・コメントに倣う）
- [ ] 予約するAPIと、予約を取得するAPIが動く
- [ ] 予約は既存の3層構造（Controller/Service/Mapper+XML/エンティティ/DTO）に**馴染む形**で実装
- [ ] 異常系（存在しない本/利用者を予約 → 404 など）を、既存の `common/` の例外の仕組みで扱う
- [ ] 単体テスト（Service層）を足し、`./gradlew test` が**全緑**
- [ ] 既存のテーブル・機能を壊していない

---

## 3. 着地点のヒント（週6の読解を、新規エンティティに応用）

「既存のエンティティ1つ分（例: book）」をお手本にすると迷いません。

- `reservation/` パッケージを新設し、`Reservation` / `ReservationController` / `ReservationService` / `ReservationMapper`(+XML) / DTO を、**book の構成をなぞって**作る。
- `db/schema.sql` に `reservations` を追加（`lendings` が books/members を参照しているのと同じFKの書き方に倣う。DROP順にも注意）。
- 起動クラスの `@MapperScan("com.example.training")` はルートを見ているので、新パッケージのMapperも自動で拾われる（＝ここは触らなくてよい。確認しておくと安心）。

> **設計判断のポイント（PRで説明を求められる）**: 「同じ本・同じ人が重複予約できていいか」「在庫があるとき予約を許すか」「予約に状態(status)を持たせるか」。正解は1つではありません。**決めて、理由を言えること**が大事です。

## 5. レビュー観点（出す前に自分でも確認）

- **既存の作法に馴染んでいるか**: book/lending をなぞった3層構造・命名・DTO分離になっているか。浮いていないか。
- **schema の追加が正しいか**: FK・DROP順・コメントが既存の書き方に揃っているか。既存テーブルを壊していないか。
- **設計判断に理由があるか**: 重複予約・在庫ありのときの扱い・statusの有無について、**なぜそうしたか**を説明できるか。
- **異常系**: 存在しない本/利用者の予約を、既存の例外の仕組み（404）で扱えているか。
- **テストの意味**（週8）: 予約の正常系・異常系を意味のあるアサーションで確かめているか。
- **影響範囲**（週7）: 既存の貸出・返却・在庫の動きに影響を与えていないか。
