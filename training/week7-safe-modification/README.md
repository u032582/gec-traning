# 週7: 安全な改修 — 既存リポを壊さずに直す

週6で「読む」を身につけました。今週は、いよいよ**既存のコードに手を入れます**。ただし現場で一番大事なのは「直す」こと自体ではなく、**周りを壊さずに直す**ことです。
配属先であなたが最初に任されるのは、たいてい「このバグを直して」「この小さな機能を足して」です。そのとき、直した拍子に**別の動いていた所を壊す（リグレッション）**のが、新人が最もやりがちな事故。今週はそれを防ぐ動き方を身につけます。
全体の進め方・AI利用ルール・質問テンプレート・日報フォーマットは、先に [研修トップのREADME](../README.md) を読んでください。

> この週は第2フェーズ（AI協働）の後半です。**AIに改修案を出させてよい**——ただし「AIが直したから大丈夫」ではなく、**なぜその変更で直るのか／他に影響が出ないかを自分で判断できること**が条件。週5・週6で培った「疑って裏を取る」が、ここで「壊さず直す」に結実します。

---

## 1. この週の狙い（到達目標）

> **既存リポのバグ票・小さな機能要望を渡されたら、周りを壊さずに直して、テストを通せる。**

この週で身につけること:

- **影響範囲を見極める**: 変更する前に「これを直すと、どこに波及するか」を追う
- **リグレッションを防ぐ**: 変更前後で**全テストを流し**、直した所以外を壊していないか確認する
- **既存の規約に合わせる**: 自分流で書かず、周りのコードの命名・書き方に馴染ませる
- **変更を小さく保つ**: 直すべき所だけ直す。ついでのリファクタで範囲を広げない
- **Gitでブランチを切ってPRで出す**: 現場の提出フロー（同一リポ・ブランチ・PR）を通す

> 用語メモ: **リグレッション** … 直したつもりが、別の動いていた箇所を壊してしまうこと。**既存テストを流して**、壊していないか確認するのが基本動作。
> 用語メモ: **影響範囲** … その変更が波及する範囲。「この関数を直すと、呼んでいる側はどこか／このデータを触ると、他のどの処理が読むか」を追うこと。

## 2. AI利用区分（この週のルール）

✅ **週7は、AIに改修案を出させてよいです。** ただし条件が厳しくなります。

- ✅ AIに「このバグの直し方」「この機能の追加案」を出させてよい
- ✅ ただし採用する前に、**なぜその変更で直るのか**を自分の言葉で言えること
- ✅ そして **他に影響が出ないか（影響範囲）** を自分で確認すること
- 🚫 **全テストが緑になっていない改修は提出不可**（直した所だけでなく、既存テストも緑のまま）

> AIは「バグを直すコード」を出すのは得意ですが、「**その変更が他を壊さないか**」までは保証してくれません。そこを見るのが人間の仕事です。この週は、AIの改修案に対して「直る理由」と「影響範囲」の2点を自分で埋められるかが勝負です。

理由の詳細は [研修トップのREADME「2. AI利用ルール」](../README.md#2-ai利用ルール最重要必ず守る) を参照。

## 3. 練習の題材（bug-scenarios ミニプロジェクト）

この週の課題は、[bug-scenarios/](bug-scenarios/) という**練習用のミニプロジェクト**で行います。
これは題材リポ（図書貸出管理API）の**貸出まわりを切り出し、わざとバグを仕込んだ**ものです。

- テストは **DBを使いません**（Mockitoで完結）。だから `./gradlew test` だけで正誤が判定できます。
- いま走らせると、**いくつかのテストが赤（FAILED）**になります。それが「仕込まれたバグ」のサインです。
- あなたの仕事は、**テストを手がかりにバグを見つけ、`LendingService.java` を直して、全部緑にする**こと。

### まず、赤を見る
```bash
cd bug-scenarios
./gradlew test
```
`FAILED` のテストが2つ出ます。**どのテストが・何を期待して落ちているか**をよく読んでください。そこにバグの在り処が書いてあります。

> ⚠️ **テストは書き換えないでください。** 直すのは `src/main/java/.../LendingService.java` の方です。テストを緩めて緑にするのは、体温計を割って熱が下がったことにするのと同じ。テストは「あるべき仕様」を表しています。

## 4. この週の進め方（1課題のサイクル）

現場の改修は「いきなり直す」ではありません。次の順で進めます。**この順番自体が今週の学び**です。

1. **赤を読む**: `./gradlew test` で落ちているテストを読み、「何がおかしいか」をつかむ。
2. **原因を特定する**: `LendingService.java` を読み、バグの箇所を見つける（`// TODO(bug-N)` が目印）。
3. **影響範囲を先に言う**: 直す前に「この変更で、他のどこに影響するか」を**改修ノート**に書く。
4. **小さく直す**: 直すべき所だけ直す。AIに案を出させてよいが、採用理由を言えること。
5. **全テストを流す**: `./gradlew test` が**全部緑**になったことを確認（＝直った＋壊していない）。
6. **ブランチを切ってPRで出す**（課題03）。

## 7. Git / PR のおさらい（週7以降ずっと共通）

この研修では、現場（SES＝客先の社内リポにメンバーとして参画）に合わせ、**同じリポをcloneし、作業ブランチを切ってPRを出す**やり方で統一します。

```bash
git switch -c fix/lending-stock     # ①作業ブランチを切る
# …直す。こまめにコミット…
git add . && git commit -m "fix: 在庫切れ時に貸出記録を作らないよう修正"
git fetch origin                    # ②origin/master を最新化（他の人の変更を取り込む）
git push -u origin fix/lending-stock # ③push
# ④GitHub等でPRを作る → レビュー往復 → master へマージ
```

> **フォーク（fork）は使いません。** SES現場ではほぼ使わない形なので、この研修では扱いません。`fork` や `upstream` は今は覚えなくて大丈夫。詳しくは課題03と [週4のGit手順](../week4-test-and-final/README.md#6-git--prプルリク提出の手順--初心者向け) を参照。
