# 課題02: バグ②を直す — 返却しても在庫が戻らない

**所要時間の目安**: 90分
**AI利用区分**: ✅ AIに改修案を出させてよい。ただし「なぜ直るか」「影響範囲」を自分で言えること。

---

## 1. 背景・狙い（現場でどう使うか）

課題01と同じ「赤→直す→緑」のサイクルですが、今回のバグは**「やるべき処理が丸ごと抜けている」**タイプです。エラーは出ないのに、静かにデータが壊れていく——現場で怖いのはこういうバグです。テストがあるからこそ気づけます。

---

## 2. バグの症状（バグ票のつもりで読む）

> **バグ票**: 本を返却したあと、その本の「貸出可能数（available_count）」が**増えない**。
> 借りるときは減るのに、返しても戻らない。何度か貸し借りするうちに、在庫が実際より少なく見え、
> やがて「在庫があるのに貸せない」状態になる。

まず赤を見ます。
```bash
cd ../bug-scenarios
./gradlew test
```
`返却_在庫が1戻る()` が **FAILED** のはずです。テストを開き、**何が呼ばれることを期待して落ちているか**（ヒント: `verify(bookMapper).incrementAvailable(...)`）を読んでください。

---

## 3. やること

### ステップ1: 原因を特定する
`LendingService.java` の `returnBook` メソッドを読みます。`// TODO(bug-2)` が目印。返却の手順は「①記録を確認 → ②返却済みにする → ③**在庫を戻す**」のはず。**③が抜けている**ことに気づけるか。

### ステップ2: 影響範囲を先に言う
「在庫を戻す1行」を足すと、他に影響はあるか？ 課題01で直した `lend` の側に波及しないか？ 二重返却を弾くテスト（もともと緑）を壊さないか？——を改修ノートに先に書きます。

### ステップ3: 小さく直す
`returnBook` の中に、在庫を1戻す処理を1行足します。**どのメソッドを呼べばいいか**は、`lend` 側で在庫を減らしている処理（`decrementAvailable`）の"逆"を探すと見つかります（`BookMapper` を開いてみてください）。

### ステップ4: 全テストを流す
```bash
./gradlew test
```
ここで **`BUILD SUCCESSFUL`（全部緑）** になれば、課題01・02の両方が直り切ったということです。

> 課題01を先に直していれば、ここで全5テストが緑になります。もし01のぶんが赤いままなら、先に01を仕上げてください。

## 5. つまずきポイントとヒント

<details>
<summary>「在庫を戻すメソッド」が分からない</summary>

`BookMapper.java` を開いてください。`decrementAvailable`（1減らす）の隣に、対になるメソッドがあるはずです。返却は「借りるの逆」なので、減らすの逆＝増やすメソッドを、返した本のIDに対して呼びます。返した本のIDは `lending.getBookId()` で取れます。
</details>

<details>
<summary>どこに1行足せばいい？</summary>

`returnBook` の `// TODO(bug-2)` のコメントがある位置です。「返却済みにする」処理の後、「最新状態を返す」の前。順番も意味があります（先に返却済みにしてから在庫を戻す）。
</details>

<details>
<summary>なぜテストが無いと危ないのか、ピンと来ない</summary>

このバグは**例外もエラーも出ません**。画面上は「返却できました」と正常に見えます。人が手で確認していたら見逃します。`verify(bookMapper).incrementAvailable(1L)` という「呼ばれるべき処理が呼ばれたか」を見るテストがあったからこそ、静かな不具合が赤で表面化しました。これが週8（テストで品質を担保）につながります。
</details>
