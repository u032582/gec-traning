# 課題03: ブランチを切ってPRで出す — 現場の提出フロー

**所要時間の目安**: 90分
**AI利用区分**: ✅ コミットメッセージやPR本文の下書きをAIに手伝わせてよい。ただし内容は自分の言葉に直すこと。

---

## 1. 背景・狙い（現場でどう使うか）

現場では、直したコードを「はい直しました」と口で言うのではなく、**ブランチを切ってPR（プルリク）で提出**します。レビュアーが差分を見て、指摘を返し、往復して、最後にmasterへ取り込む。この**提出のフロー自体**が、現場で毎日使う基本動作です。

この研修が想定する現場は **SES（客先の社内リポにメンバーとして参画）**。だから **同じリポをcloneし、作業ブランチを切ってPRを出す**やり方だけを練習します。OSSでよく使う**フォーク（fork）は使いません**（SES現場ではほぼ出番がないため）。

> 用語メモ: **PR（プルリク / プルリクエスト）** … 「このブランチの変更を取り込んでください」とレビュー依頼を出す仕組み。差分（変更点）と「何を・なぜ変えたか」を添える。

---

## 2. 前提

課題01・02で、`bug-scenarios/` のバグを直し、`./gradlew test` が全部緑になっていること。その**直した状態**を、これから提出フローに乗せます。

## 3. やること

### ステップ1: 作業ブランチを切る
本流（master）から枝分かれします。ブランチ名は `fix/やること` の形が現場の慣習です。
```bash
git switch -c fix/lending-stock-integrity
```

### ステップ2: 意味のある単位でコミットする
「バグ①の修正」「バグ②の修正」のように、**1つの意図＝1コミット**が読みやすいです。まとめて1コミットでも可ですが、メッセージは規約（`fix:` 始まり）に沿わせます。
```bash
git add .
git commit -m "fix: 在庫切れ時に貸出記録を作らないよう修正し、返却時に在庫を戻すよう修正"
```
> コミットメッセージの下書きはAIに手伝わせてよいですが、**何を直したか自分で分かる言葉**にすること。

### ステップ3: origin を最新化してから push
他の人の変更を取り込んでから push するのが安全です（今は一人でも、現場の癖として身につける）。
```bash
git fetch origin          # origin/master の最新を取得
git push -u origin fix/lending-stock-integrity
```

### ステップ4: PRを作る
GitHub等の画面で「Compare & pull request」からPRを作成します。本文には最低限これを書きます。
```
## やったこと
- 在庫切れの本を貸そうとしたとき、貸出記録を作らず409を返すよう修正（bug-1）
- 返却時に、その本の在庫（available_count）を1戻すよう修正（bug-2）

## なぜ直るか
- lend: decrementAvailable が0（在庫切れ）のとき例外を投げ、insert まで進ませない
- returnBook: markReturned の後に incrementAvailable を呼び、在庫を戻す

## 動作確認
- ./gradlew test が全緑（BUILD SUCCESSFUL）
- 既存の正常系テスト（正常な貸出・二重返却の拒否）も緑のまま（リグレッションなし）

## 影響範囲
- 変更は LendingService の lend / returnBook のみ。テストは変更していない
```

> リモートが無い/まだ用意されていない場合は、[週4のGit手順のフォールバック](../week4-test-and-final/README.md#リモートが無い--まだ用意されていない場合フォールバック)（`git log --oneline` と `git diff` で対面提示）に従ってください。

## 4. 完成条件（自分で判定できる）

- [ ] `fix/...` のブランチを切って作業した
- [ ] `fix:` 始まりの意味あるコミットメッセージでコミットした
- [ ] push して PR を作った（リモートが無ければ差分を対面提示できる状態にした）
- [ ] PR本文に「やったこと」「なぜ直るか」「動作確認（全緑）」「影響範囲」を書いた

## 5. つまずきポイントとヒント

<details>
<summary>フォーク（fork）しなくていいの？</summary>

いりません。この研修（SES想定）では、**同じリポに直接ブランチを切ってPR**を出します。フォークは「権限のない外部の人がOSSに貢献する」形で、客先リポに招かれて参画するSESの実態とは合いません。`fork` / `upstream` という言葉は今は覚えなくて大丈夫です。
</details>

<details>
<summary>コミットは1つ？ 2つに分けるべき？</summary>

どちらでも構いませんが、**「1つの意図＝1コミット」**が読みやすいのは確かです。bug-1とbug-2は別の不具合なので、2コミットに分けると、レビュアーが「どの変更が何のためか」を追いやすくなります。現場では「読みやすい差分」も評価対象です。
</details>

<details>
<summary>PR本文に何を書けばいいか分からない</summary>

レビュアーの気持ちで考えます。「この人は何を・なぜ変えて・壊していないとどう確認したか」が知りたい。だから「やったこと／なぜ直るか／動作確認／影響範囲」の4点。上のテンプレートをベースに、自分の言葉で埋めてください。
</details>
