# 課題03: silent failure（静かな失敗）を暴く

**所要時間の目安**: 120分
**AI利用区分**: ✅ AIに相談してよい。ただし「握りつぶし」を見抜く判断は自分がすること。

---

## 1. 背景・狙い（現場でどう使うか）

現場で一番こわいバグは、**エラーも出ないのに、こっそり間違った結果を返す**ものです。例外が出れば気づけますが、例外を**握りつぶして"それっぽい値"を返す**コードは、誰も気づかないまま被害を広げます。これを **silent failure（静かな失敗）** と呼びます。

AIは、こういう「例外を握りつぶして安全そうな値を返す」コードを、**むしろ親切心で書きがち**です。そしてそのコードに対するテストも「握りつぶした結果」を"正しい"と固定してしまいがち（課題01の見本Dがまさにそれ）。この課題では、silent failure を**見抜き、その危うさを暴くテスト**を書きます。

---

## 2. 対象

[test-quality-lab/src/main/java/com/example/training/lending/OverdueChecker.java](../test-quality-lab/src/main/java/com/example/training/lending/OverdueChecker.java)。
「貸出が延滞しているか」を判定するクラスです。まず読んでください。**どこかに"握りつぶし"があります。**

---

## 3. やること

### ステップ1: 握りつぶしを見つける
`isOverdue` メソッドを読み、`try-catch` に注目します。`catch` の中で何をしているか。**例外が起きたとき、どんな値を返しているか。** それは「本当に正しい」のか、それとも「問題を隠している」のか。

### ステップ2: 「隠れている問題」を具体化する
握りつぶしがあると、どんな入力で問題が起きるかを考えます。ヒント: `dueDate`（返却期限）が `null` の貸出を渡すと、中で何が起きて、最終的に何が返るか。**本当は延滞かもしれないのに、"延滞ではない"と言い切っていないか？**

### ステップ3: 危うさを暴くテストを書く
`OverdueChecker` の silent failure を**問題として突く**テストを、新しいファイル（例: `OverdueCheckerTest.java`）に書きます。方針は2つのどちらか（両方でもよい）:

- **(a) あるべき姿を主張するテスト**: 「dueDate が null のような異常データは、false で握りつぶさず、例外を投げる（or 呼び出し側に気づかせる）べきだ」というテストを書く。**今の実装ではこのテストは赤くなる**——それが「silent failure がある」証拠。
- **(b) 正常系はしっかり守るテスト**: 期限切れ未返却→true、返却済み→false、といった**意味のあるアサーション**で、正しい判定は緑にしておく。

> ⚠️ ここが今週の核心: (a)のテストは**わざと赤くする**ことで「今の実装には問題がある」と示します。「テストは緑にするもの」という思い込みを外してください。**赤いテストが"直すべき所"を指し示す**こともあるのです。

### ステップ4: どう直すべきかを言葉にする（直すのは任意）
silent failure をどう直すべきか（例: `dueDate` が null なら例外を投げる／呼び出し側で弾く）を、品質ノートに書きます。実際に `OverdueChecker` を直して(a)を緑にできたら、なお良し（余力があれば）。

---

## 品質ノート（この課題の提出物・必ず埋める）

```
【OverdueChecker の"握りつぶし"はどこか（該当箇所）】


【その握りつぶしで、どんな入力のとき・何が隠れるか】


【書いたテスト】
 - (a) 危うさを暴くテスト: 何を主張し、今の実装で赤/緑どちらになったか
 - (b) 正常系を守るテスト : 何を確かめ、緑になったか

【この silent failure は、どう直すべきか（自分の考え）】


【なぜ silent failure は"エラーが出るバグより怖い"のか、自分の言葉で】

```

## 5. つまずきポイントとヒント

<details>
<summary>catch で false を返して何が悪いの？「安全側」では？</summary>

「延滞ではない(false)」は、**延滞の見逃し**につながります。督促が飛ばず、本が返ってこない。つまり false は「安全側」ではなく「問題を隠す側」。しかも例外を握りつぶすので**ログにも残らず、誰も気づけない**。異常なデータ（dueDateがnull等）が来たら、false で流さず「おかしい」と気づける形にすべきです。
</details>

<details>
<summary>「わざと赤くするテスト」の意味が分からない</summary>

テストは「緑にするため」だけのものではありません。「**今の実装は、あるべき姿になっていない**」ことを示すためにも使えます。あるべき姿（dueDate=nullなら例外）を主張するテストを書けば、今の握りつぶし実装では赤くなる。その赤が「ここに直すべき問題がある」という指差しです。直したら緑になります。
</details>

<details>
<summary>AIに聞いたら「この実装は安全で問題ない」と言われた</summary>

まさにそれがAIの落とし穴です。AIは「例外を握りつぶす」コードを"親切な安全策"と見なしがち。**AIの「問題ない」を鵜呑みにしない**。dueDateがnullの貸出を渡したら本当に正しい結果になるか、自分でテストして確かめてください。週5〜7で鍛えた「疑って裏を取る」を、ここで使います。
</details>
