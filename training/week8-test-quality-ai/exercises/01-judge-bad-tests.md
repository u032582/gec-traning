# 課題01: ダメなテストを見抜く

**所要時間の目安**: 90分
**AI利用区分**: ✅ 判断の相談にAIを使ってよい。ただし採用/却下の最終判断は自分がすること。

---

## 1. 背景・狙い（現場でどう使うか）

AIにテストを書かせると、たくさん・速く出てきます。しかもたいてい**緑（PASSED）**になります。でも「緑＝良いテスト」ではありません。**何も確かめていないのに緑になるテスト**が量産されることがあります。それを受け入れてしまうと、「テストがある安心感」だけあって、実は何も守られていない——という一番危ない状態になります。

この課題では、**わざと出来の悪いテストの見本**を読み、1本ずつ「採用/却下」を判断し、**なぜダメか**を言語化します。これが、AIの出したテストを選別する目の土台です。

---

## 2. 対象

[test-quality-lab/src/test/java/com/example/training/lending/BadTestExamplesTest.java](../test-quality-lab/src/test/java/com/example/training/lending/BadTestExamplesTest.java) の見本A〜D。まず走らせて、**全部緑になる**ことを確認してください。
```bash
cd ../test-quality-lab
./gradlew test
```

---

## 3. やること

### ステップ1: 1本ずつ「これは何を確かめている？」と問う
見本A〜Dを1つずつ読み、こう自問します:
- このテストは、**もし実装にバグが入ったら、赤くなって気づけるか**？
- それとも、実装がどうであれ**必ず緑になる**か？（＝何も守っていない）

### ステップ2: 採用/却下を判断し、理由を書く
各見本を「却下」（＝こんなテストは書くべきでない）と判断し、**なぜダメか**を品質ノートに書きます。ヒント（各見本の狙い）:
- **見本A**: アサーションの中身をよく見て（`result` と何を比べている？）
- **見本B**: アサーションが1つも無い。何を確かめている？
- **見本C**: モックにした `Lending` の値を確認している。テスト対象（OverdueChecker）は動いている？
- **見本D**: 緑だが、`OverdueChecker` の"ある挙動"を「正しい」と固定してしまっている。その挙動は本当に正しい？（課題03の伏線）

### ステップ3: カバレッジの数字を、自分の目で見る（ここが今週の急所）

「カバレッジの数字に騙されるな」と言われても、**その数字を一度も見たことがなければピンと来ません**。だから先に見ます。

`./gradlew test` を叩くと、テストと一緒にカバレッジのレポートも作られています。ブラウザで開いてください。
```
test-quality-lab/build/reports/jacoco/test/html/index.html
```
（Cursorのエクスプローラで右クリック →「Open with Live Server」でも、ファイルをブラウザにドラッグしても構いません）

開いたら `com.example.training.lending` → **`OverdueChecker`** の行を見てください。

> **約87%** と出ているはずです。

いま `test-quality-lab` にあるテストは、**あなたが却下したばかりの見本A〜Dだけ**です。つまりこの87%は、**何ひとつ確かめていない4本のテストだけで叩き出した数字**ということになります。

ここで一度、頭の中で実験してみてください。`OverdueChecker.java:31` の判定が、うっかり逆（`isBefore` を `isAfter`）に書き間違えられたとします。延滞を延滞と判定できない、立派なバグです。

- **カバレッジの数字は下がるでしょうか？** → ほとんど変わりません。**通る行は同じ**だからです。
- **見本A〜Dは赤くなるでしょうか？** → **なりません。4本とも緑のまま**です（何も確かめていないので、実装がどうであれ緑）。

つまり、この87%という数字が保証しているのは **「その行を通った」ことだけ**。**「その行が正しい」とは、一言も言っていません。**

> 用語メモ: **jacoco（ジャコロ）** … Javaのカバレッジを測る道具。`./gradlew test` を叩くと自動でレポートが出るよう、この練習用プロジェクトに仕込んであります。

この「**数字は高いのに、何も守られていない**」状態を目で見たことが、今週いちばんの収穫です。品質ノートに、いま見た数字を書き留めておいてください。

### ステップ4: 1本を「良いテスト」に書き直す
見本A〜Dのうち1つ（おすすめは見本A）を、**意味のあるテスト**に自分で書き直します。`BadTestExamplesTest.java` は触らず、**新しいファイル**（例: `MyGoodTest.java`）を `src/test/java/com/example/training/lending/` に作って書きます。
- 「延滞している貸出を渡したら true が返る」「返却済みなら false」など、**実装にバグが入れば赤くなる**アサーションにすること。
- `./gradlew test` で、自分の書いたテストが緑になることを確認。

> ヒント: `OverdueChecker.isOverdue(lending, asOf)` に、期限切れ（dueDateが過去）で未返却の Lending を渡せば true、返却済み（returnedAtあり）なら false。この「入力と期待の対応」があるのが良いテストです。

```

 - 見本B: 却下 / 理由:
 - 見本C: 却下 / 理由:
 - 見本D: 却下 / 理由（何を"正しい"と固定してしまっているか）:

【カバレッジの数字（ステップ3で自分の目で見たもの）】

 - この数字が保証していること／していないこと:

 - もし実装にバグが入ったら、このテストは赤くなるか（なぜそう言えるか）:

【「緑＝良いテストではない」を、自分の言葉でまとめると】

```

## 4. 完成条件（自分で判定できる）

- [ ] 見本A〜Dすべてを「却下」と判断し、**なぜダメか**を1本ずつ書いた

- [ ] 1本を「良いテスト」に書き直し、`./gradlew test` で緑にした

## 5. つまずきポイントとヒント

<details>
<summary>見本Aのどこがダメか分からない</summary>

`assertThat(result).isEqualTo(result)` を見てください。`result` を `result` 自身と比べています。これは**実装がどうであれ必ず true**（同義反復＝トートロジー）。`isOverdue` が常に false を返すバグが入っても、このテストは緑のまま。だから何も守っていません。
</details>

<details>
<summary>見本Bは「例外が出ないこと」を確かめているのでは？</summary>

その意図ならアリな場合もありますが、このテストは**アサーションが1つも無い**ので「例外が出ないこと」すら明示していません（たまたま例外が出なければ緑）。カバレッジ（実行行数）は上がるので「テストした感」は出ますが、正しさは保証しません。これが「カバレッジ稼ぎ」の典型です。
</details>

<details>
<summary>却下ばかりで、採用は無いの？</summary>

この課題の見本A〜Dは、**学習用に全部ダメなもの**を集めています。だから全部却下でOK。現場では「採用できるもの」も混じるので、次の課題02で「AIの出力から採用/却下を選り分ける」練習をします。
</details>
