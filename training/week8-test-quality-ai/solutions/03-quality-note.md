# 模範: 課題03 品質ノート（記入例）

> これは**記入の見本**です。大事なのは「握りつぶし」を見抜き、その危うさを「わざと赤くするテスト」で示せていること。

---

【OverdueChecker の"握りつぶし"はどこか（該当箇所）】
 `isOverdue` の `try-catch`。`catch (Exception e)` の中で、例外の中身を見ずに `return false;` している。エラーをログにも出さず、握りつぶして「延滞ではない」を返している。

【その握りつぶしで、どんな入力のとき・何が隠れるか】
 `dueDate` が null の貸出を渡すと、`lending.getDueDate().isBefore(asOf)` で NullPointerException が起きる。だが catch がそれを握りつぶして false を返す。結果、**本当は延滞しているかもしれない（データがおかしい）貸出が、"延滞ではない" として見逃される**。しかも例外が消えるので、誰もデータのおかしさに気づけない。

【書いたテスト】
 - (a) 危うさを暴くテスト: OverdueCheckerExposeTest.java に「dueDate=null の貸出を渡したら、false で握りつぶさず例外を投げるべき」というテストを書いた。→ **今の実装では赤くなった**（実装は false を返すので、例外を期待する assert が失敗）。これが「silent failure がある」証拠。
 - (b) 正常系を守るテスト: dueDate=2026-07-01・未返却 を asOf=2026-07-18 で判定 → true（延滞）。返却済み → false。両方 **緑**。正しい判定はちゃんと守れている。

【この silent failure は、どう直すべきか（自分の考え）】
 catch で全部握りつぶすのをやめる。dueDate が null のような異常データは、false で流さず、明示的に弾く（例: 最初に `if (lending.getDueDate() == null) throw new IllegalArgumentException(...)` で気づける形にする）。少なくとも、握りつぶすなら**ログには残す**べき。「静かに」消してはいけない。

【なぜ silent failure は"エラーが出るバグより怖い"のか、自分の言葉で】
 エラーが出るバグは、出た瞬間に気づけて直せる。silent failure は**エラーが出ない**ので、間違った結果が"正しいふり"をして流れ続ける。延滞の見逃しが積み重なっても、誰も気づかない。気づいたときには被害が大きくなっている。「気づけない」ことが一番の害。

---

## この記入例で見てほしいポイント

- 握りつぶしを「catch で return false」と**具体的に特定**し、隠れる問題（延滞の見逃し・例外が消える）を挙げている。
- **「わざと赤くするテスト」(a)** で「今の実装は、あるべき姿になっていない」を示せている（テスト＝緑にするもの、の思い込みを外せている）。
- 直し方を「握りつぶさない・弾く・ログに残す」と具体化している。
- 「気づけないことが一番の害」と、silent failure の本質を言語化できている。
