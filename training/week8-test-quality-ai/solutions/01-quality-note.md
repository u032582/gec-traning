# 模範: 課題01 品質ノート（記入例）

> これは**記入の見本**です。大事なのは「緑/赤」ではなく「何を守っているか」で判断できていること。

---

【見本A〜D それぞれの判定と理由】
 - 見本A: 却下 / `assertThat(result).isEqualTo(result)` は `result` を自分自身と比べているだけ。実装がどうであれ必ず緑（同義反復）。isOverdue が常に false を返すバグが入っても気づけない＝何も守っていない。
 - 見本B: 却下 / アサーションが1つも無い。メソッドを呼ぶだけ。カバレッジ（実行行数）は上がるが、戻り値も副作用も検証していない。「テストした感」だけで正しさは保証ゼロ。
 - 見本C: 却下 / モックにした Lending の `getDueDate()` に値を仕込み、その仕込んだ値を確認しているだけ。テスト対象の OverdueChecker の判定ロジックを1行も通っていない。テスト対象を取り違えている。
 - 見本D: 却下 / dueDate=null で false になることを「正しい」と緑で固定している。だが OverdueChecker は内部で例外を握りつぶして false を返しているだけ（silent failure）。このテストはバグを"仕様"として追認してしまっている（課題03で扱う）。

【自分で書き直した「良いテスト」（どの見本を、どう直したか）】
 - ファイル名: MyGoodTest.java（src/test/java/com/example/training/lending/ に新規作成）
 - 何を入力に、何を期待するテストにしたか: dueDate=2026-07-01・returnedAt=null の貸出を、asOf=2026-07-18 で判定 → 期限切れ未返却なので isOverdue が **true** を返すことを assert。加えて、returnedAt有り（返却済み）なら **false** を assert。
 - もし実装にバグが入ったら赤くなるか: なる。例えば isOverdue が「常に false」になったら、true を期待する1本目が赤くなる。「入力→期待」が対応しているので、判定ロジックが壊れれば検知できる。

【「緑＝良いテストではない」を、自分の言葉でまとめると】
 テストが緑なのは「そのテストが要求したことが満たされた」だけ。要求が空っぽ（何も確かめない）なら、緑でも意味は無い。良いテストは「もし実装が間違ったら赤くなる」もの。緑かどうかではなく「**間違いを捕まえられるか**」で価値を測る。

---

## この記入例で見てほしいポイント

- 4本すべてに「**なぜ実装のバグを捕まえられないか**」の理屈がある（「なんとなくダメ」で済ませていない）。
- 見本Dについて「silent failure を仕様として固定している」と、課題03につながる危うさに気づいている。
- 書き直したテストが「**入力→期待の対応**」を持ち、「バグが入れば赤くなる」と説明できている。
