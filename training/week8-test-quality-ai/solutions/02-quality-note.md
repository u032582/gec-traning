# 模範: 課題02 品質ノート（記入例）

> これは**記入の見本**です。AIの出力は毎回違うので、本数や内訳はあなたのものに置き換えてください。
> 大事なのは「採用/却下を理由つきで判断し、抜けを自分でも探した」こと。

---

【AIに書かせたテストの本数と、採用/却下の内訳】
 - 生成された本数: 6本
 - 採用: 3本
   - 正常な貸出で decrementAvailable と insert が呼ばれる（verify で確認）
   - 在庫切れ(decremented==0)で BusinessRuleException が投げられ、insert が呼ばれない
   - 借り主がいないとき NotFoundException（memberService.findById が例外）
 - 却下: 3本
   - 「lend が null を返さないこと」だけ確認（assertThat(result).isNotNull() のみ＝薄い）
   - when(...) の設定だけで assert も verify も無い（見本Bと同型のカバレッジ稼ぎ）
   - 正常系のほぼ同じテストが2本（重複。1本で足りる）

【却下したテストの中で、一番「危なかった」もの と その理由】
 「lend が null を返さないこと」だけを見るテスト。緑になるし一見それらしいが、在庫の増減も記録作成も**何も確かめていない**。もし insert を呼び忘れるバグが入っても、null でなければ緑のまま。「テストがある安心感」だけ与えて実は守っていない、が一番危ない。

【AIが「不足ケース」として挙げたものは妥当だったか。自分で追加で見つけた抜けは】
 AIは「返却(returnBook)のテストが無い」と正しく指摘した（妥当）。一方でAIは「貸出履歴(findByMember)のテスト」には触れなかった。自分で気づいて追加した。また週7で直したバグ「返却で在庫が戻る(incrementAvailable が呼ばれる)」のテストも抜けていたので足した。

【最終的に、LendingService の何を守るテストが揃ったか（自分の言葉で）】
 貸出の正常系（在庫が減り記録ができる）／在庫切れの拒否（記録を作らない）／借り主・本の不在(404)／返却の正常系（在庫が戻る）／二重返却の拒否。＝「在庫の整合」と「異常系の拒否」を守るテストが揃った。バグが入れば、対応するテストが赤くなる状態にできた。

## この記入例で見てほしいポイント

- 採用/却下を**本数だけでなく中身の理由**で説明している。
- 「一番危なかったテスト」に、課題01で学んだ「緑だが何も守っていない」を当てはめている。
- **AIの不足指摘を検算**し、AIが見落とした抜け（履歴・週7のバグ対応）を自分で足している（AIに任せきりにしていない）。
