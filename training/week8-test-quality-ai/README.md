# 週8: テストと品質をAIで担保する — 最終判断は人間が持つ

週7で「壊さず直す」を身につけました。今週は、その直したコードに**テストを足して品質を守る**——ただし**AIと協働で**やります。
AIはテストを書くのが速い。でも「そのテストが本当に意味のある検証になっているか」「カバレッジの数字に騙されていないか」は、AIには保証できません。**最終的な品質判断を人間が持つ**——それが今週のテーマです。
全体の進め方・AI利用ルール・質問テンプレート・日報フォーマットは、先に [研修トップのREADME](../README.md) を読んでください。

> この週は第2フェーズ（AI協働）の後半です。**AIにテストを書かせてよい・レビューさせてよい**——ただし「AIが書いたテストが緑だから安心」ではなく、**そのテストが何を守っているかを自分で判断できること**が条件。週5〜7で培った「疑って裏を取る」を、テストの品質に向けます。

---

## 1. この週の狙い（到達目標）

> **AIにテストを書かせ・レビューさせつつ、最終的な品質判断は自分が持てる。**

この週で身につけること:

- **AIにテストを書かせる/不足を指摘させる**: 効くプロンプトでテストを生成させ、抜けたケースを洗い出させる
- **テストの良し悪しを人間が判断する**: 意味のないアサーション・カバレッジ稼ぎのテストを**見抜く**
- **silent failure（静かな失敗）を見抜く**: 例外を握りつぶして"それっぽい値"を返すコードの危うさに気づき、それを暴くテストを書く
- **AIレビューの取捨選択**: AIのコードレビュー指摘を「採用/却下」し、その理由を言語化する

> 用語メモ: **アサーション** … テストの中で「結果はこうなっているはずだ」と**断言する**行のこと。`assertThat(result).isEqualTo(3)` のように書く。英語の **assert（アサート）＝「断言する」** がカタカナになっただけで、**週4で書いた `assertEquals(...)` と同じもの**を指す（[週4の用語メモ](../week4-test-and-final/README.md#1-この週の狙い到達目標)）。カタカナで出てきても新しい概念ではないので身構えなくてよい。**この行が無いテストは、実行しただけで何も確かめていない**——今週はここを見抜く。
> 用語メモ: **カバレッジ** … テストで実行されたコードの割合（%）。数字が高い＝良いテスト、ではない。「実行はしたが何も確かめていない」テストでもカバレッジは上がる。**数字に騙されない**のが今週の肝。**言葉で納得しなくて大丈夫**——課題01で、アサーションが1つも無いダメなテストでもカバレッジの数字が上がることを、自分の目で見てもらいます。
> 用語メモ: **silent failure（サイレントフェイラー／静かな失敗）** … エラーを出さずに、こっそり間違った結果を返してしまうこと。例外を握りつぶして"安全そうな値"を返すコードが典型。エラーが出ないぶん、誰も気づかず被害が広がる。

## 2. AI利用区分（この週のルール）

✅ **週8は、AIにテストを書かせ・レビューさせてよいです。** ただし条件があります。

- ✅ AIにテストを書かせてよい／「不足しているケースは？」と聞いてよい
- ✅ ただし出てきたテストを **1本ずつ「採用/却下」で判断**し、理由を言えること
- ✅ 「緑になった」で終わらせない。**そのテストが何を守っているか**を自分の言葉で
- 🚫 意味のないアサーション・カバレッジ稼ぎのテストを、判断せずそのまま採用は不可

> AIは「通るテスト」を量産できますが、「**意味のあるテスト**」かどうかは別問題です。今週は、AIの出したテストの中から**使えるものを選び、ダメなものを見抜く**目を鍛えます。この目が、現場で「AIにテストを任せても品質を落とさない人」を作ります。

理由の詳細は [研修トップのREADME「2. AI利用ルール」](../README.md#2-ai利用ルール最重要必ず守る) を参照。

## 3. 練習の題材（test-quality-lab）

この週の課題は、[test-quality-lab/](test-quality-lab/) という練習用プロジェクトで行います。
題材リポの貸出まわり（正しい実装）に加え、**わざと出来の悪いテスト群**と、**silent failure が仕込まれたクラス**が入っています。

- `src/test/.../BadTestExamplesTest.java` … **AIが出しがちな"ダメなテスト"の見本**（課題01で批評する）
- `src/main/.../lending/OverdueChecker.java` … **silent failure が潜むクラス**（課題03で暴く）

まず走らせてみましょう。
```bash
cd test-quality-lab
./gradlew test
```
`BadTestExamplesTest` の見本A〜Dが**全部緑（PASSED）**になります。**でも、この4つは全部ダメなテストです。** 「緑＝良いテスト」ではないことを、まず体感してください。

> ⚠️ `BadTestExamplesTest.java` は**書き換えないでください**。批評の対象として読みます。良いテストは、あなたが別ファイルに書きます。

## 4. この週の進め方（1課題のサイクル）

1. 対象（ダメなテスト群／AI生成テスト／silent failureクラス）を読む。
2. **1本ずつ「採用/却下」を判断**する。緑かどうかではなく、「何を守っているか」で判断する。
3. 判断を **品質ノート**（各課題に雛形あり）に、理由つきで書く。
4. ダメなものは、**意味のある良いテストに書き直す**（自分の手で）。
5. `./gradlew test` で、自分の書いた良いテストが緑になることを確認する。

> この週の提出物は**品質ノート**（採用/却下の記録）＋**自分で書き直した良いテスト**です。「AIがこう書いた」ではなく、「このテストは○○を守っているから採用／○○を確かめていないから却下」と、**判断の理由**が書けていることがゴールです。
