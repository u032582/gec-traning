# 週5: AI協働の作法 — 任せる/任せないの線引きと、生成物の検証

ここから研修の後半に入ります。週3〜4で「AIにコードを書かせて、理解して、説明する」の素振りをしました。
この週は一歩踏み込んで、**AIを"使いこなす"側の作法**——どこまで任せてよいか、生成物のどこを疑い、どう裏を取るか——を体に入れます。
全体の進め方・AI利用ルール・質問テンプレート・日報フォーマットは、先に [研修トップのREADME](../README.md) を読んでください。

> この週は第2フェーズ（AI協働）のまん中です。**AIにコードを書かせてよい**——それどころか、この週は「AIに書かせること」が課題そのものです。ただし目的は"楽をする"ことではありません。**AIの出力を評価し、間違いを見つけ、直せるようになる**ことがゴールです。週6以降（既存リポへの参画）で、この「疑って裏を取る」力がそのまま武器になります。

---

## 1. この週の狙い（到達目標）

> **AIにコードを書かせ、それを自分の言葉で説明でき、間違いを見つけて直せる。**

週3〜4では「AIに書かせて、動いたらOK」に近い進め方でも通れました。この週はそこを一段引き上げます。
**「動いた」は入口にすぎない**——本当に仕様どおりか、境界値を取りこぼしていないか、そのメソッドは実在するか、既存コードに馴染むか。これを**毎回チェックする癖**を付けます。

この週で身につけること:

- **AIの基本操作**: 仕様・制約・期待出力を渡す「効くプロンプト」の書き方
- **生成コードの検証**: 出てきたコードを鵜呑みにせず、レビュー観点（後述）で1つずつ確かめる
- **AIが間違える典型パターンを体で知る**: それっぽいが動かない／古い書き方／存在しないメソッド（ハルシネーション）
- **任せる/任せないの線引き**: AIに任せてよい作業と、人間が判断すべき作業の見分け

> 用語メモ: **ハルシネーション** … AIが、それっぽいが事実でないこと（存在しないメソッド名・古いAPIなど）を、自信満々に出力すること。AIを使う以上、これを見抜く力が必須です。この週で実際に1回"踏んで"もらいます。
> 用語メモ: **検証（けんしょう）** … 「本当にそうか」を自分で確かめること。AIが「これで動きます」と言っても、そのまま信じないで、テストを流す・仕様と突き合わせる・実際に呼んでみる、で裏を取ること。

## 2. AI利用区分（この週のルール）

✅ **週5は、AIにコードを書かせてよいです。むしろ「書かせること」が課題です。**

ただし、この週の"提出物"は**動くコードではありません**。**検証ノート**です。

- ✅ AIに書かせたコードを、**レビュー観点（§4）で1つずつ確かめた記録**を残すこと
- ✅ 「なぜこの実装なのか」「どこを疑い、どう裏を取ったか」を**自分の言葉で書けること**
- 🚫 検証ノートが空欄・「動いたのでOK」だけ、は提出不可です

> この週の本質は「AIに任せて楽をする」ではなく、「**AIを疑い、自分の判断を上に置く**」練習です。現場でAIを使う人の"安全装置"を、自分の中に作る週だと思ってください。中身を理解せず貼るだけの人は、現場で信用されません。

理由の詳細は [研修トップのREADME「2. AI利用ルール」](../README.md#2-ai利用ルール最重要必ず守る) を参照。

## 3. この週の進め方（週1〜4の"やり直し"で学ぶ）

この週は**新しい題材を持ち込みません**。**すでに自分で解いた週1〜4の課題を、今度は「AIに書かせて→検証して→説明する」形でやり直します。**

なぜ既習の課題を使うのか。**答えを自分が知っているから**です。週1〜2は自分の手で書いた正解が手元にあります。だから「AIの出力が正しいか」を、自分の答えと突き合わせて判定できます。**正解を知っている題材でAIの癖を体で知る**——これが、正解を知らない現場でAIを見極める力の土台になります。

1課題のサイクル:

1. `exercises/NN-xxx.md` を開いて、その日の**お題（どの既習課題をAIにやらせるか）**を確認する。
2. AIに、仕様・制約・期待出力を渡して**コードを書かせる**（効くプロンプトの書き方は課題01で練習）。
3. 出てきたコードを、**そのまま信じない**。§4のレビュー観点で1つずつ確かめる。
4. 確かめた結果を **検証ノート**（各課題に雛形あり）に自分の言葉で書く。
5. 自分が週1〜2で手書きした答え（`solutions/` や自分の提出物）と**見比べて**、AIの癖・違いに気づく。

> ⚠️ ここで大事なのは「AIの答えと自分の答え、どちらが正しいか」を**自分で判定できること**です。判定できないなら、それは§4の観点のどれかが埋まっていないサインです。

## 4. AI生成コードのレビュー観点（この週の"ものさし"・毎回使う）

これは [curriculum.md](../curriculum.md#ai生成コードのレビュー観点第2フェーズで毎回使う) にある、第2フェーズ共通の"安全装置"です。**週5で使い方を体に入れ、週6以降もずっと使います。**

| 観点 | 問い |
|---|---|
| **動くか** | 本当にビルドが通り、テストが通るか？（AIは動かないコードも自信満々に出す） |
| **正しいか** | 仕様どおりか？ 異常系・境界値を取りこぼしていないか？ |
| **存在するか** | 使われているメソッド・APIは実在するか？（ハルシネーション） |
| **古くないか** | 非推奨・時代遅れの書き方ではないか？ |
| **馴染むか** | 既存コードの規約・命名・構造に合っているか？（浮いていないか） |
| **壊さないか** | 既存の動いている箇所に影響しないか？（リグレッション） |
| **説明できるか** | なぜこの実装なのか、自分の言葉で言えるか？ |

> 1つでも「No」または「分からない」があれば、それは**まだ提出してはいけない**サインです。

## 7. もっとやりたい人へ（追加課題）

- 週3〜4のAPI課題を1本、AIにゼロから書かせ、`./gradlew test` と curl の両方で裏を取ってみる。
- わざと**曖昧なプロンプト**（例:「顧客を取得するAPIを作って」だけ）で書かせ、何が抜け落ちるかを観察し、プロンプトを直して比べる。
- AIに「このコードをレビューして」と自分の週1〜2の手書き解を渡し、返ってきた指摘の**妥当性を自分で選別**してみる（採用/却下と理由）。
