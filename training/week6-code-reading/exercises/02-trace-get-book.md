# 課題02: 書籍取得の流れを追う（GET /api/books/{id}）

**所要時間の目安**: 90分
**AI利用区分**: ✅ 読解の相棒としてAIを使ってよい。ただしAIの言う「ファイル・行」を必ず自分で開いて確かめること。

---

## 1. 背景・狙い（現場でどう使うか）

全体像（課題01）が見えたら、次は**1つの機能の処理フローを、端から端まで追う**練習です。「このAPIを叩くと、どのファイルのどのメソッドを、どの順で通って、最後にSQLが走るのか」を追えるようになると、「ここを直したい」というとき**該当箇所に最短でたどり着ける**ようになります。

この課題では、一番シンプルな **書籍1件取得 `GET /api/books/{id}`** を題材に、Controller → Service → Mapper → XML(SQL) の流れを1本、通しで追います。

---

## 2. やること

### ステップ1: 入口（Controller）から追い始める

`GET /api/books/{id}` を受けるのはどこか。まず `book/` パッケージの Controller を開きます。

- どのメソッドが `GET /api/books/{id}` を受けているか（ヒント: `@GetMapping("/{id}")`）
- そのメソッドは、次にどこ（どのクラスのどのメソッド）を呼んでいるか

### ステップ2: 1段ずつ、呼び出しをたどる

Controller が呼んでいる Service、Service が呼んでいる Mapper、Mapper に対応する XML(SQL) …と、**呼び出しを1段ずつ**下っていきます。各段で「どのファイルの何行目か」をメモします。

追う流れ（これを自分で埋める）:
```
Controller の受け口
  → Service の何というメソッド
    → Mapper の何というメソッド
      → XML の <select id="..."> の実際のSQL
```

### ステップ3: AIに流れを要約させ、裏取りする

AIにこう聞いてもよい:
```
このリポで GET /api/books/{id} を叩いたとき、
どのファイルのどのメソッドを順に通ってDBアクセスまで行く？ファイル名と行番号で。
```

返ってきた「ファイル名・行番号」を、**1つずつ実際に開いて確かめます**。AIが挙げた行に、本当にそのメソッドがあるか。**行番号がズレていることはよくあります**——そこを自分で正すのが裏取りです。

### ステップ4: 「見つからないID」のときはどうなるか

`GET /api/books/999`（存在しないID）を叩くと404が返ります。**その404は、どのファイルのどの行で決まっているか**も追ってください（ヒント: Service で例外を投げ、`common/` の何かが受けている）。

## 4. つまずきポイントとヒント

<details>
<summary>Mapperには「メソッドの形」しか無い。SQLはどこ？</summary>

`@Mapper` の付いたインタフェース（`BookMapper.java`）には、メソッドの宣言だけがあります。実際のSQLは、同じ名前の `<select>`/`<update>` として `src/main/resources/mapper/BookMapper.xml` に書かれています。**インタフェースのメソッド名とXMLの `id` が一致**することでつながっています（週3で学んだ形）。
</details>

<details>
<summary>行番号がAIの言う場所とズレている</summary>

それが**普通**です。AIはコードの内容から「たぶんこの辺」を推測して行番号を言いますが、正確とは限りません。**自分でファイルを開いて、実際の行を数える**のが正解。エディタの行番号表示を使ってください。このズレに気づけたら、それは立派な裏取りです。
</details>

<details>
<summary>404の流れが追えない</summary>

`BookService` で本が見つからないとき、何かを `throw` しています。その「投げられたもの」を受け取って404に変えているのが `common/` の中にあります。「throw」でリポを検索（`grep -rn throw src/main`）すると入口が見つかります。
</details>
